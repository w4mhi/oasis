ADS-B Aircraft

Hear and map nearby aircraft on 1090 MHz with a cheap RTL-SDR — offline

ADS-B puts nearby aircraft on the same live map as APRS. A cheap RTL-SDR dongle tuned to 1090 MHz hears the Mode S / ADS-B broadcasts that airliners and most GA aircraft send continuously — position, altitude, speed, and callsign — and OASIS decodes, records, and plots them with no internet and no subscription.

⚠

ADS-B holds the RTL-SDR exclusively. Only one consumer can own a dongle at a time, so ADS-B is mutually exclusive with the APRS SDR feed, satellite listen, and OpenWebRX on the same dongle. It ships off by default and is started on demand by routing a dongle to it. A second dongle lets you run both at once.

Turning it on

⚠

The ADS-B card has no START / STOP button. ADS-B is one of the hardware-routed services: you start it by routing an RTL-SDR to it in the SRV OPS hardware console, and stop it by taking the device away. The card’s only button is OPEN ↗, which opens the traffic map, and it stays disabled until the service is up. See Service Operations. You still need service controls enabled — the console uses the same sudoers grant.

ADS-B installs two systemd units, both disabled until a device is routed to them. Starting also enables them and stopping also disables them, so the station comes back after a power cut in the state you left it.

UnitRole
dump1090-faThe Mode S / ADS-B decoder (installed via apt). Owns the RTL-SDR and writes live positions to aircraft.json.
adsb-apiOASIS’s own recorder + history API on :8086. Polls aircraft.json, records observations to a local SQLite database, evaluates alerts against your station location, and serves it all to the map.

Install happens through the setup menu or directly: 

python3 services/adsb/install.py           # installs dump1090-fa + the adsb-api unit
python3 services/adsb/install.py --serve   # run the recorder/API in the foreground (dev)

Reading the map

With ADS-B running, the map’s right rail gains two panels. The behaviour mirrors the APRS layer so there is nothing new to learn:

  • ADS-B N aircraft — the live list, each row an ICAO hex or flight number with its current altitude. Altitude is colour-coded (low to high) and the same colour tints the aircraft icon on the map, so a glance shows who is on approach versus overflying at cruise.
  • ADS-B Alerts — see below.

Where a flight number resolves to an operator, OASIS tags it from an offline airline table (common/js/adsb-operators.js) — no lookup call leaves the box.

⚠

The shipped operator table is a 37-entry seed of major carriers, not the full ~1500-entry table. Most flights you hear will therefore show no operator tag at all — that is expected, not a bug. Regenerate it with scripts/build-adsb-operators.py, which needs an OpenFlights airlines.dat dropped in scripts/data/ first; that file is not in the repo, so this is an online, one-time job. The tag also needs a real airline callsign (three letters then a digit) — a tail number like N12345 never resolves to an operator.

Alerts

There are exactly two alert rules, and neither is about altitude:

  • Emergency squawk — 7500 (unlawful interference), 7600 (radio failure), 7700 (general emergency). These alert at any distance.
  • Proximity — the aircraft is inside a radius of your station.
⚠

The map computes its own alerts, client-side. It bands them at 15 km (green), 5 km (amber) and 2 km (red), from your station position and the live aircraft list, refreshed every 2 s. Those thresholds are fixed in the map. The server-side ADSB_ALERT_RADIUS_KM (default 50 km) governs only what the daemon logs to its database and returns from /alerts — and nothing in the UI reads that endpoint. Changing the env var will not change a single thing you see.

Each alert row shows the callsign or ICAO hex, then either the squawk code and its meaning (for an emergency squawk) or the distance from your station. Bearing is never shown — the aircraft’s own track appears in the popup, but that is its heading, not a bearing from you. Emergency squawks sort to the top, then nearest first; the card shows the closest ten and summarises the rest. The panel auto-expands the first time an alert appears and re-arms when it empties.

From the operator’s point of view this is a live view of what is up there right now, not a log you scroll back through. (The daemon does keep a 200-entry in-memory ring and a permanent alert_events table, but nothing on screen reads either.) Repeat alerts for the same aircraft and rule are suppressed for five minutes.

Signal health

The dashboard’s ADS-B card carries a flow meter. Its bar and its UP / SILENT verdict are driven by samples_per_sec — the dongle’s sample throughput — and explicitly not by the message rate. Real ADS-B traffic is sparse: a perfectly healthy receiver can go a full minute seeing one message. Judging health on message rate would call a working station dead every quiet hour. The N msg/min text beside the bar is a label only; it never decides anything.

A blue meter means samples are flowing. Red / SILENT means the unit is up but the front end is deaf — check the antenna and the RF chain, not the software.

The history API

⚠

The adsb-api daemon binds 127.0.0.1 only. Querying http://<pi>:8086/… from another machine will always fail — that is by design, not a firewall problem. The map reaches it through the Flask proxy at /api/adsb/* on the normal :8083, same origin. To poke the daemon directly, do it on the Pi (curl -s localhost:8086/health) or go through the proxy from anywhere.

EndpointReturns
GET /healthPoller liveness: last_json_age_s (a growing age means dump1090-fa stopped feeding), aircraft_count and positioned. Once stats.json has produced a usable window it also returns samples_per_sec, messages_per_min, flowing, plus signal_dbfs and noise_dbfs. This is what drives the signal meter.
GET /aircraftThe current live snapshot (what the map plots).
GET /history?since=<ts>&icao=<hex>Recorded observations from the SQLite history database.
GET /alertsRecent squawk / proximity alert events from the in-memory ring. Nothing in the UI consumes this.

The Flask proxy at /api/adsb/health flattens this into a fixed envelope that always carries the same keys (null where unknown), and drops the two dBFS figures — those never reach the browser. flowing is tri-state: null means stats.json has not been written yet, which is not the same as “no signal”.

ℹ

The recorder is a separate daemon from the Flask app. If you change ADS-B recorder code, restart it with sudo systemctl restart adsb-api — restarting the OASIS web server alone will not pick it up.

Retention

The history database holds two tables that behave differently. The aircraft table is a latest-position snapshot, one row per ICAO, and is never pruned — it is what “recently heard” reads, which is why that query is cheap. The observations table is the detailed track, and it is the only thing pruned: rows older than 120 hours (five days) are deleted, immediately at daemon start and then every 600 seconds.

A breadcrumb row is only written when a frame actually carries a changed position — repeated identical positions and Mode-S-only frames are roughly 80% of traffic and are dropped. Without that, an unbounded observations table reaches millions of rows in a month. Set ADSB_RETAIN_HOURS=0 to disable pruning entirely if you are keeping a research log and have the disk for it.

Configuration & off-Pi testing

Environment variables override the defaults, which also lets you run adsb.serve() on a laptop with no dump1090-fa by pointing it at a saved JSON file and a writable database path:

VariableDefaultPurpose
ADSB_JSON_PATH/run/dump1090-fa/aircraft.jsonThe live aircraft JSON to poll
ADSB_STATS_PATH/run/dump1090-fa/stats.jsondump1090-fa’s statistics file — the source of samples_per_sec and therefore of the signal meter
ADSB_DB_PATH/var/lib/adsb/adsb-history.dbSQLite history database
ADSB_API_PORT8086HTTP API port (loopback only)
ADSB_ALERT_RADIUS_KM50Proximity radius for the server-side alert log only — it does not affect the map
ADSB_POLL_SECS1.0Poll interval for aircraft.json
ADSB_RETAIN_HOURS120How long detailed observations are kept. 0 disables pruning.
ADSB_PRUNE_EVERY_S600How often the prune loop runs

The station position is not an environment variable — it comes from configuration/station.json. Without it no proximity alert can ever be produced (squawk alerts still are).

Troubleshooting

SymptomCause & fix
Dashboard card is grey / NOT INSTALLED ADS-B isn’t installed. Run python3 services/adsb/install.py (or pick it in the setup menu), then reload the dashboard.
The card has no START button By design — route a dongle to ADS-B in the SRV OPS console instead. See Service Operations.
It fails to come up, or the APRS feed died when you routed the dongle to ADS-B Expected on a single dongle — they share it, and routing displaces whatever held it. Fit a second RTL-SDR to run both. Check journalctl -u dump1090-fa -e for usb_claim_interface error -6 (dongle busy).
Card is UP but 0 aircraft Decoder running, nothing heard. 1090 MHz is line-of-sight — you need a clear-sky antenna. Confirm decodes at the source: journalctl -u dump1090-fa -f. A basic dongle whip indoors hears little.
Map plots nothing but the list has aircraft The map needs your station position and a base map for the area. Aircraft without a position fix (message-only) never plot.
/health shows a growing age dump1090-fa stopped writing aircraft.json. Restart it: sudo systemctl restart dump1090-fa. If adsb-api code changed, also sudo systemctl restart adsb-api.
No alerts ever fire Proximity alerts are relative to your station — set position on the GPS card. Beyond that there is nothing to widen: the map alerts at a fixed 15 km and ADSB_ALERT_RADIUS_KM does not touch it. If nothing comes within 15 km, no proximity alert is correct.
The meter says SILENT but the unit is up Samples are not flowing — an RF-chain problem, not software. Check the antenna, the connector and the dongle. 1090 MHz is line-of-sight.
Almost no flight shows an operator name Expected: only 37 carriers ship in the seed table. Regenerate it with scripts/build-adsb-operators.py and an OpenFlights airlines.dat.
curl <pi-ip>:8086/health refuses the connection The daemon is loopback-only. Run the curl on the Pi itself, or go through the Flask proxy at /api/adsb/health on :8083.
